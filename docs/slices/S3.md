# Slice S3: verified stabiliser chain behind the group interface

**Goal.** Replace the explicit-enumeration group backend by a deterministic Schreier–Sims construction with an independent verifier, provenance for strong generators, sifting, base change, the §7.2 tuple minimum and pointwise-stabiliser orbits, behind the unchanged `canon_group_ops` interface of S1. Every S1 and S2 test and end-to-end tier must produce byte-identical results with the new backend. Groups whose order does not fit the explicit table (for example `Sym(12)`) become usable.

Normative text: `docs/specification.md` v2.0 (cited §x): §§3, 7.1, 7.2, 8.1, 9.1, 9.2, 9.3, 11.1. Process and interfaces: `docs/detailed-implementation-plan.md` §0, §0a, §2.2, §2.3, §5 (WP2.2–2.5). Prerequisites: S1 and S2 landed. The S1 §2 rules apply unchanged.

## 1. Scope

In scope:

- `src/bsgs/chain.{h,c}`: chain data (§2.3 of the detailed plan), the practical deterministic constructor (§9.1 second paragraph), sifting and membership, order, point-stabiliser suffix, base change by rebuild, tuple minimum, orbits of a pointwise stabiliser.
- `src/bsgs/reference.c`: the direct Schreier recursion of §9.1 first paragraph, used only by tests as the correctness anchor for small groups.
- `src/bsgs/verify.c`: the independent verifier of §9.1 third paragraph.
- `src/bsgs/provenance.{h,c}`: straight-line derivation records `INPUT i | INVERSE j | PRODUCT j k` for every stored strong generator (§9.2).
- `src/perm/`: a sparse (moved-support) representation and a tagged identity if the chain needs them (§9.3); otherwise document why dense suffices for S3.
- `src/bsgs/chain_backend.c`: the `canon_group_ops` implementation over the chain; `canon_group_create` builds it by default. The explicit backend stays, selectable through a new context option, as a test oracle.
- Public API: a context option to select the backend; `canon_group_order` accessor returning `uint64_t` with a documented capacity (see §3.5).
- Tests: C unit tests for every piece; byte identity of the chain against the explicit backend on T1 and on the S1/S2 e2e tiers; the T2 random-group tier.
- READMEs; `docs/slices/S3-notes.md`.

Out of scope: the coset enumerator and least-element-with-constraints descent (S4), canonical `Group(H)` bytes (S4), multi-limb orders beyond `uint64` (S4 introduces `canon_nat` with the group encoding), randomised construction, performance work on chain construction (M5), compact Schreier-tree records and dense transporter caches beyond the simple form below (M5).

## 2. Design

### 2.1 Chain data (`src/bsgs/chain.h`)

```c
typedef struct canon_bsgs_level {
    uint32_t base_point;
    uint32_t orbit_len;  uint32_t *orbit;        /* orbit[0] == base_point; discovery order */
    uint32_t *orbit_pos;                         /* n entries: position in orbit or NONE */
    uint32_t *parent_point, *parent_gen;         /* Schreier vector over `orbit` positions */
    uint32_t gen_count;  uint32_t *gen_ids;      /* indices into the chain's generator table */
} canon_bsgs_level;

typedef struct canon_bsgs {
    uint32_t n, depth;
    canon_bsgs_level *levels;        /* levels[i] generates G_(b_0..b_{i-1}); levels[depth] is trivial */
    canon_perm_table gens;           /* all strong generators, dense; with provenance ids */
    canon_provenance prov;
    uint64_t order;                  /* product of orbit lengths; CAPACITY_LIMIT if it overflows */
    bool verified;                   /* set only by canon_bsgs_verify */
} canon_bsgs;
```

The generator table stores each strong generator once, dense, together with its inverse (computed on insertion, with provenance `INVERSE`), so that transporter reconstruction never recomputes inverses.

### 2.2 Construction (`chain.c`), policies fixed by the detailed plan §5 WP2.3 (§9.1)

Input: the validated generators of `canon_group_create`. Deterministic closure:

1. Normalise the input generator list: drop identities, drop duplicates (exact array equality), keep the first occurrence order. Record each kept generator as `INPUT i`.
2. Base extension rule: when a residue fixes every current base point and is not the identity, append its least moved point as the next base point.
3. Insertion level: a residue is inserted at the deepest level whose base prefix it fixes pointwise.
4. After inserting at level `i`: recompute orbit, Schreier vector and `orbit_pos` for levels `≥ i` (queue traversal from the base point in increasing discovered-label order, generators in `gen_ids` order; a point discovered through generator `s` from point `p` records `parent_point = p`, `parent_gen = s`). Then re-sift every Schreier generator `t_b s t_{b^s}⁻¹` of every level `≥ i`, in level order then orbit order then generator order, inserting failed residues as in 3 and restarting the pass from the lowest affected level. Terminate when a complete pass inserts nothing.
5. Every insertion must strictly enlarge the subgroup represented at its level: before inserting, sift the residue through the current chain and insert only the nonidentity remainder. This bounds the number of insertions by the length of a chain of subgroups.
6. Provenance: a Schreier generator is `PRODUCT(PRODUCT(t_b, s), INVERSE(t_{b^s}))` where `t_b` is itself a product along the Schreier tree; record transporters as products of generator ids along the tree path so that the provenance DAG stays polynomial (§9.2 "do not expand long words repeatedly").

Transporter `t_b` (the element of the level's group sending the base point to `b`) is reconstructed by walking the Schreier vector from `b` to the root and composing the recorded generators in the right order under the convention `(pq)[v] = q[p[v]]`: if the path is `b_0 → b_1 → … → b`, with `b_{j+1} = b_j^{s_j}`, then `t_b = s_0 s_1 … s_{k-1}` as a left-to-right product. Test this convention explicitly on a 3-cycle.

Counters (`canon_bsgs_stats`): candidates considered, sifts, dense compositions, insertions, passes.

### 2.3 Verifier (`verify.c`) (§9.1 third paragraph)

Write `verify.c` from the spec's list without consulting `chain.c`'s construction code; it may use only `perm.h`, `provenance.h` and the chain data layout. It checks, and fails on the first violation with an enum naming it:

1. every stored generator is a bijection of the domain;
2. every stored generator's dense array equals the array re-derived from its provenance record, recursively down to `INPUT` entries, which must equal the original validated input generators;
3. level `i` generators fix `b_0 … b_{i-1}` pointwise;
4. each orbit's points are reachable from the base point through the stored Schreier edges, and `orbit_pos` inverts `orbit`;
5. each orbit is closed under the level's generators;
6. the reconstructed transporter `t_b` sends the base point to `b` for every `b` in the orbit;
7. every Schreier residue `t_b s t_{b^s}⁻¹` sifts to the identity through levels `> i`;
8. every original input generator sifts to the identity from the root;
9. the last level is trivial (`gen_count == 0`);
10. `order` equals the product of orbit lengths (or the chain is marked as exceeding `uint64`).

`canon_bsgs_verify` sets `verified = true` only when all pass. Conditions 7, 8 and 9 together give both inclusions (§9.1: "Induction gives both inclusions at every level and completeness").

### 2.4 Operations (§§7.2, 9.2)

- `sift(g)`: for each level, `b = g[base_point]`; if `b` not in orbit, fail at that level; else `g ← g · t_b⁻¹`. Membership iff the final residue is the identity. (Check the side: with right actions `g t_b⁻¹` fixes the base point when `g` sends it to `b`.)
- `order`: product of orbit lengths with overflow detection.
- `point_stabiliser(k)`: the suffix view from level `k` is `G_(b_0..b_{k-1})`.
- `rebase(prefix)`: rebuild the chain from the current strong generators with the requested ordered base prefix, then verify. (Reuse of existing levels is optional and not required in S3.)
- `tuple_min(L)` (§7.2): `t = id`, `H = G`; for `i` in order: `a = t[L[i]]`; `b = min(a^H)` where `a^H` is the orbit of `a` under `H` (computed as the orbit of the first level of a chain for `H` rebased to start at `a`, or by a union-find over `H`'s generators); `u = t_b` of that level; `t ← t u`; `H ← H_b` (the suffix after fixing `b`). Implementation: maintain `H` as a chain rebased so that its base starts with the points `L[0]^t, L[1]^t, …` as they are fixed; one rebase per step is acceptable in S3 (document the cost as O(n) rebuilds per call). The orbit ids of `G_M` for the G stage are the orbits of the final `H`'s generators by union-find, ranked by least point (§7.1 ordering), on target labels, exactly as the explicit backend returns them.
- `contains(p)`: sift.

### 2.5 Backend selection and capacity

Add to `canon_capacity`: nothing. Add to the context a `canon_backend` enum `{CANON_BACKEND_CHAIN /* default */, CANON_BACKEND_EXPLICIT}` set through a new `canon_context_set_group_backend(ctx, backend)` (provisional until M4). `max_group_order` now applies to the explicit backend only; the chain reports `CANON_CAPACITY_LIMIT` from `canon_group_create` only when the order product overflows `uint64` (document that S4's `canon_nat` lifts this). Add `canon_group_order(const canon_group *, uint64_t *out)` to the public header.

## 3. Tests

- `tests/c/test_chain.c`: on every T1 group (built from the greedy generators) and on 200 seeded random generator sets with `n ≤ 8`: order equals the explicit backend's; membership agrees with the explicit table for all elements and for 200 random non-members; `tuple_min` (`t` and orbit ids) equals the explicit backend's on random lists `L` of every length `0..n`; rebase to random prefixes preserves order and membership; the verifier accepts every built chain. Also `Sym(12)` from two generators: order `479001600`, membership of random products, `tuple_min` on a full list is the identity when `L` is increasing; and an `n = 64` cycle (long Schreier path): order 64.
- `tests/c/test_reference_schreier.c`: the §9.1 direct recursion on T1 groups agrees with the chain on order and membership.
- `tests/c/test_verify.c`: ten distinct mutations of a verified chain (flip an orbit entry, swap a Schreier parent, drop a generator, corrupt a provenance record, change a base point, truncate the last level, alter `order`, duplicate an orbit point, reverse a transporter edge, change an input generator) are each rejected with the matching reason.
- `tests/c/test_provenance.c`: re-derivation of every strong generator from provenance equals the stored array; the DAG size is polynomial (assert an explicit bound such as `nodes ≤ 4 · insertions · n` and record the measured value in the notes).
- Byte identity: run `tests/python/test_e2e.py` with the chain backend (the default) and again with `CANON_BACKEND=explicit` exported to the CLI through a new `--backend` option; both runs must agree with the Python model. Add a `make check` line for the explicit run.
- Capacity: `canon_group_create` on `Sym(21)` generators returns `CANON_CAPACITY_LIMIT` with the chain backend (order exceeds `uint64`), and the test says why in a comment.
