# Slice S8: capacity admission, live-memory ledger, metrics, `solve_batch`, sink pause, fault injection and fuzz targets

**Status: written and implemented 13 October 2026 by one agent on the maintainer's instruction ("work by yourself; grind through the next steps"); decisions below are the implementer's, recorded for the maintainer's review.** Normative text: `docs/specification.md` v2.1 §3.2, §11.1–11.3, §12.1, §14.1, §17, §19, §20, §22. Process: `docs/detailed-implementation-plan.md` §0a (S8 row), WP4.8, WP5.1, WP5.2; `docs/slices/S8-batch-reading.md` §5 (the maintainer's batch decision D12, now spec §17 v2.1). Prerequisites: S1–S7b.

## 1. Scope

In scope:

1. **`canon_solve_batch`** exactly as spec §17 v2.1 states it (D12): call-level `INVALID_INPUT` only for a NULL workspace, NULL arrays with `count > 0` or a `count` whose byte size overflows; otherwise every input attempted in caller order on the one workspace (`CALLER_THREADS`, §14.1), `statuses[i]`/`results[i]` exactly what `canon_solve` gives for that input alone (a NULL entry: `INVALID_INPUT` for that entry only); the call returns `COMPLETE` iff every input was attempted; admission and quota per input. Cancellation is not offered (not decided, §14.3 later).
2. **Output sink pause and resume** (§17 "`PAUSE` retains the offset for resume, `FAIL` returns `OUTPUT_ERROR`. No bytes are skipped or duplicated on resume."): `canon_result_encode_resume(result, &offset, sink, user)` streams from `*offset` and leaves in `*offset` the number of bytes accepted so far; a sink return of 1 pauses with status `CANON_CANCELLED` (§3.2's interrupted status; the result is unchanged and the offset is the resume point), any other nonzero return or zero progress is `CANON_OUTPUT_ERROR`. `canon_result_encode` is the call with offset 0 whose pause is likewise `CANON_CANCELLED` (S1 treated it as a failure).
3. **Live-memory ledger** (§11.2, WP5.1): every allocation of the library goes through `src/arena/mem.h` (`canon_mem_malloc`/`calloc`/`realloc`/`free`), which keeps the process-wide live byte count and peak (each block carries its size in a header), so that `M_live` of §11.2 is measured, not estimated; the public `canon_mem_stats` reports live and peak bytes and the allocation count. The ledger is process-wide (one counter set, atomic), so under `CALLER_THREADS` with several workspaces it aggregates; a per-solve peak is attributed to the solve on one thread.
4. **Deterministic capacity admission** (§11.1 "reserve a complete serial reference workspace plus bounded output/verification buffers", "if that one-task requirement exceeds the descriptor, return `CAPACITY_LIMIT` before search"): the descriptor gains `max_live_bytes` (0: the context default, `1 << 30`; implemented as `1 << 32`, `S8-notes.md` reading 4). At problem creation a **plan** is computed from the input alone, a conservative upper bound on the bytes the serial solve allocates beyond its inputs (partition and snapshot stacks, refinement scratch, the leaf image, the certificate buffers when requested, the enumeration and stabiliser scratch; the group and the objects themselves are charged as their measured sizes, which are functions of the input), and the problem is refused with `CAPACITY_LIMIT` when the plan exceeds the budget. The plan is the policy (§11.1): the actual peak is measured by the ledger and reported, and a test checks measured peak ≤ plan on every tier; exceeding the plan at run time is never a status (that would make the status schedule-dependent), it is a planning defect to fix.
5. **Metrics** (§19, WP5.2, §8.3 "must appear in metrics"): a fixed-layout `canon_metrics` on every result (`canon_result_metrics`): P1 nodes, leaves, images materialised, children explored and pruned, automorphism candidates and insertions (explicit and implicit), stabiliser rebases, enumeration visits, stabiliser hits and verified rebuilds, coset descents and transient rebuilds, character evaluations, the signed fast path, root-discrete and singleton-orbit indicators (§7.3 "Record root-discrete and singleton-orbit frequencies separately"), output bytes, certificate bytes, the planned bytes and the measured peak live bytes of the solve. No times (no benchmark before M5, HANDOFF).
6. **Fault injection** (WP4.8): `canon_mem_fail_after(k)` makes the k-th following allocation fail (internal header, used by `tests/c/test_faults.c`); for every k on a small suite of every objective, the solve either completes or returns `RESOURCE_LIMIT`, every handle stays releasable, nothing leaks (ASan) and a later solve on the same workspace succeeds (§17 "Allocator failure leaves the old state or a releasable partial state, never a fabricated completion flag").
7. **Fuzz targets** (WP4.8): `fuzz/fuzz_cdag_decode.c` (the stream decoder and validator through the public API) and `fuzz/fuzz_checker.c` (`canon-check`'s rules on arbitrary bytes); each has a `LLVMFuzzerTestOneInput` entry and, so that no libFuzzer runtime is needed here, a standalone driver that replays a seed corpus with deterministic mutations (`make fuzz`, bounded iterations, also a ctest entry). The checker target shares no code with `src/` (it compiles the checker's sources).

Out of scope: pool execution of batches (§14.1 `CORE_POOL`, M6), cancellation, checkpoints, the strict memory fallback of §11.2 (one mutable state with branch recipes; M5/M6), per-stage times, GPU ledgers, benchmark policy (M5).

## 2. Decisions (implementer's, for review)

- **D15 Pause status.** A paused sink is reported as `CANON_CANCELLED` with the offset retained, since §3.2's enum is frozen and has no `PAUSED`; the resume entry point distinguishes it from a cancelled solve by its contract. Alternative considered: a new status value (rejected: §3.2 freezes the eight).
- **D16 Plan versus measurement.** Admission is by plan; the ledger measures; the status never depends on the measurement. The plan is deliberately loose (quadratic in `n` for the snapshot and decision stacks, which the search needs in the worst case of depth `n`), so the default budget `1 << 30` admits every input the test tiers use; a test records plan and peak for the notes.
- **D17 Process-wide ledger.** One atomic counter set, no per-workspace arena yet (worker-local arenas are M5); the per-solve peak is `peak since solve entry` and is exact when one solve runs at a time.
- **D18 Fuzzing without libFuzzer.** The harnesses carry the libFuzzer entry point for CI machines that have it, and a deterministic replay driver here; no dependency is downloaded (HANDOFF).

## 3. Tests

- `tests/c/test_batch.c`: the six tests of `S8-batch-reading.md` §5 on every T1 objective (byte identity with separate solves, a batch of 0, an invalid input among valid ones, a NULL entry, a NULL array, a per-input quota), plus certificates in a batch.
- `tests/c/test_sink.c`: pause at every offset of a stream and resume to completion, no byte skipped or duplicated; failure modes; the paused status.
- `tests/c/test_metrics.c`: counters against the internal states on the §7.4 cases; plan ≥ peak on T1 subsets and digraphs under every objective; `max_live_bytes` admission.
- `tests/c/test_faults.c`: as §1.6.
- `fuzz/`: the harnesses with a seed corpus of the golden streams and certificates; the replay driver as a ctest entry.
- `tests/python/test_e2e.py`: `canon-cli` gains `--batch` for a FORMAT run of several cases? **No**: the CLI stays one case per process (the FORMAT contract); batches are exercised in C.
