# Slice S2: coloured directed multigraphs and the O stage

**Goal.** A caller can build a coloured directed multigraph through the public API, request the P1 canonical image under a small group, and receive trace, CDAG-2 bytes, witness, status and flags. P1's O stage (arc-count signatures) is implemented. The simple-undirected-graph wrapper and the `SIMPLE-UPPER-1` key exist as library functions. `canon-cli` and the end-to-end test cover graphs and agree with the Python model and the §7.4 one-arc case.

Normative text: `docs/specification.md` v2.0 (cited §x). Process: `docs/detailed-implementation-plan.md` §0, §0a. Prerequisite: S1 landed (`docs/slices/S1.md`, `S1-notes.md`). The rules of S1 §2 apply unchanged, including: cite the spec at every rule, no golden hex in `src/` or `tools/`, strict warnings, sanitizer-clean, overflow checks, explicit `git add` paths, no push, protected files untouched.

## 1. Scope

In scope:

- `src/object/`: a **root object** abstraction over the subset (S1) and the new graph, so that refine and search dispatch on the object kind instead of being subset-specific.
- `src/object/graph.c`: import with normalisation (§4.1), CSR and CSC, colour and label interning, action (§2.1), equality.
- `src/encoding/`: the `Nat` writer (§4.1), the graph record and stream (§4.1), exact stream size, the `SIMPLE-UPPER-1` key (§4.4).
- `src/refine/`: initial key for a graph root (§7.1), the O stage with sparse signatures and the signature-to-rank split.
- `src/search/`: the search generalised to a root object; the leaf acts on the object and encodes by kind.
- `src/api/`: `canon_object_create_graph`, `canon_object_create_simple_graph`; `canon_problem_create` output-size check extended to graphs.
- `tools/canon-cli.c`: `p1-graph` subcommand.
- Tests: C unit tests for each new piece; `tests/python/test_e2e.py` extended with the graph tiers below.
- READMEs of touched modules; `docs/slices/S2-notes.md`.

Out of scope: stabiliser chains (S3), objectives other than `CANONICAL_IMAGE` (the `SIMPLE-UPPER-1` *minimum search* is S4; only the key function is built here), the CDAG-2 decoder and nested objects (S5), relations record `0a` (S5), pruning (S7), sparse-adjacency performance work beyond what is specified here (S8/M5).

## 2. Public API additions (`include/canon/canon.h`, provisional until M4)

```c
/* spec 4.1 arc record as input: source, target, label bytes, positive multiplicity */
typedef struct canon_arc {
    uint32_t source, target;
    const uint8_t *label; size_t label_length;   /* label may be NULL when label_length == 0 */
    uint64_t multiplicity;                        /* must be > 0 (spec 4.1) */
} canon_arc;

/* spec 17 builder (copies data), spec 4.1 graph semantics: `degree` vertices with colours
 * colours[v] of length colour_lengths[v] (both arrays may be NULL when degree == 0; a NULL
 * colours[v] with length 0 is the empty colour); `arc_count` arcs.  Duplicate
 * (source, target, label) arcs are combined by exact addition; a zero multiplicity is
 * CANON_INVALID_INPUT; a vertex >= degree is CANON_INVALID_INPUT; a combined multiplicity or
 * the total positive multiplicity that does not fit uint64 is CANON_CAPACITY_LIMIT (the
 * descriptor's count-bit limit is 64 in this release, detailed plan 2.1).  Loops are allowed. */
canon_status canon_object_create_graph(canon_context *ctx, uint32_t degree,
                                       const uint8_t *const *colours, const size_t *colour_lengths,
                                       const canon_arc *arcs, size_t arc_count, canon_object **out);

/* spec 4.1 simple-undirected wrapper: edges are unordered pairs {a, b}; loops (a == b) are
 * CANON_INVALID_INPUT; duplicate edges are coalesced; each edge becomes two opposite unit arcs
 * with empty labels; all vertex colours are empty.  The core never silently makes a directed
 * graph undirected: this is the only place the conversion happens. */
canon_status canon_object_create_simple_graph(canon_context *ctx, uint32_t degree,
                                              const uint32_t (*edges)[2], size_t edge_count,
                                              canon_object **out);
```

`canon_result_witness`, `canon_result_trace`, `canon_result_bytes` and `canon_result_encode` are unchanged. `canon_problem_create` accepts a graph object with objective `0x0001`; its `max_output_bytes` check uses the exact graph stream length (§11.1), which is invariant under relabelling because the colour multiset, arc count, label bytes and `Nat` lengths are unchanged by the action. Say so in a comment.

## 3. Internal design

### 3.1 Root object (`src/object/object.h`)

```c
typedef enum { CANON_ROOT_SUBSET, CANON_ROOT_GRAPH } canon_root_kind;
typedef struct canon_root { canon_root_kind kind; uint32_t n;
                            union { canon_subset subset; canon_graph graph; } u; } canon_root;
```

Functions on a root: `initial_key(root, a)` (§7.1: membership for a subset, colour rank for a graph, where colour ranks order colours by `(length, bytes)` so that increasing key equals increasing `B(colour)`); `act_into(root, g, dest, scratch)` producing the image object in caller-owned storage; `stream_write(root, buf)`; `stream_size(root, &size)`. The public `canon_object` wraps a `canon_root`. S1's subset code stays where it is; only the dispatch is new.

### 3.2 Graph (`src/object/graph.h`, `graph.c`) (§§2.1, 4.1)

Representation after import:

- `n`; `colour_id[v]` indexing a colour table sorted by `(length, bytes)` with duplicates merged; `colour_rank` therefore equals `colour_id`.
- Label table sorted by `(length, bytes)`, duplicates merged; `L` = number of distinct labels.
- Arcs: `e` records `(source, target, label_id, multiplicity)` after combining duplicates by exact addition (overflow → `CAPACITY_LIMIT`), rejecting zero multiplicities, and sorting by `(source, target, B(label))` (§4.1). Total multiplicity computed during import with overflow check (§11.1).
- CSR by source and CSC by target over the same arc records (index arrays), so that the O stage visits only incident arcs.

Action (§2.1 `ATOM-TRANSPORT-1`): `colour'[g[v]] = colour[v]`; each arc `(s, t, l, m)` becomes `(g[s], g[t], l, m)`; re-sort by `(source, target, label)`. Labels and colours are fixed byte strings and are never renamed. Equality is extensional on the normalised representation. Tests: duplicate arcs combine; `(0,0,"",1)` twice equals `(0,0,"",2)` (the n=1 loop case); zero multiplicity rejected; insertion order has no effect on the representation or the stream (§5); loops survive; a label of length 1 sorts after the empty label and `"b"` after `"a"`; a longer label sorts after every shorter one regardless of bytes.

### 3.3 Encoding (`src/encoding/`) (§4.1)

- `canon_buf_put_nat(buf, uint64_t k)`: `U32(b) || big-endian bytes of k using the shortest b`, `b = 0` for `k = 0`, no leading zero byte otherwise. Tests: 0, 1, 255, 256, 65535, 65536, 2^32 − 1, 2^32, 2^64 − 1, checked byte for byte against hand-written expectations in the test file.
- `canon_graph_stream_write(buf, graph)`: header `H(n)`, `U32(q = 1)`, record `09 || n × B(colour[v]) || U32(e) || e × (U32 source, U32 target, B(label), Nat(multiplicity))` in arc order, `U32(root = 0)`. `canon_graph_stream_size(graph, &size)` computes the exact length with overflow checks. Test: the §7.4 one-arc stream and the n=1 loop case, through the public API and the CLI, with expected hex in test files only.
- `canon_simple_upper_key(graph, buf)` (§4.4): valid only for a graph with empty colours, empty labels, no loops and exactly one unit arc in each direction per edge (return `CANON_INVALID_INPUT` otherwise, with a comment that §4.4 restricts the order to that class); emits `U32(n)` then upper-triangle bits in the order `(0,1),(0,2),(1,2),(0,3),…`, most significant bit first, final byte padded with zero low bits. Tests: `n = 0, 1, 2, 3, 4` hand-computed keys, including the padding; a directed graph with a one-way arc is rejected.

### 3.4 O stage (`src/refine/p1.c`) (§7.1)

For a graph root, at the start of each sweep take the **entry snapshot** of the ordered cells (`cell_of` and cell count `k` as they are when the sweep begins). For every vertex `v` the signature is the vector, in this index order,

```
for label rank l in 0..L-1 (labels sorted by B(label)):
    for cell index j in 0..k-1:
        out(v, l, j) = total multiplicity of arcs v -> w with label l and cell_of[w] == j
        in (v, l, j) = total multiplicity of arcs w -> v with label l and cell_of[w] == j
```

A loop `v -> v` contributes once to `out(v, l, cell_of[v])` and once to `in(v, l, cell_of[v])`. Signatures compare lexicographically with ordinary numerical order on the counts (§7.1).

**Sparse representation (decided).** The dense vector has `2·L·k` entries per vertex, which is quadratic in `n` for a discrete partition; do not materialise it. Represent a signature as the sorted list of `(index, count)` pairs with `count > 0`, where `index = ((l · k) + j) · 2 + dir` with `dir = 0` for out and `1` for in, `index` fitting `uint64_t` (overflow of `2·L·k` → `CANON_CAPACITY_LIMIT`). Build it by traversing `v`'s CSR and CSC arcs, collecting `(index, multiplicity)` pairs, sorting by index with the shared stable merge sort, and merging equal indices by exact addition (overflow → `CAPACITY_LIMIT`). Comparison of two sparse signatures `A`, `B` walks both lists: at each step compare the smaller next index; if `A`'s next index is smaller than `B`'s, then `A` has a positive count where `B` has zero, so `A > B` (and symmetrically); if the indices are equal compare the counts; if one list is exhausted the other is greater if it still has entries, else they are equal. Write this rule and its justification (it is exactly the dense lexicographic comparison with zeros elided) in a comment, and test it against a dense implementation in `tests/c/test_signature.c` on random small graphs and partitions (the dense implementation lives in the test file).

**Split by signature.** Compute all `n` sparse signatures, stable-sort vertex indices by signature, assign each distinct signature a rank in sorted order, and call S1's `split` with the ranks as keys. Since `split` orders classes within a cell by increasing key and the ranks respect the global signature order, this realises §7.1's "nonempty signature classes in increasing lexicographic signature order". Then append `STAGE_O(cell sizes)`. The G stage then reads the post-O partition exactly as in S1.

Scratch for the O stage lives in `canon_p1_scratch` (pairs buffer sized by the graph's arc count times two, per-vertex offsets, rank array) and grows only.

### 3.5 Search (`src/search/p1_tree.c`)

`canon_p1_search_subset` becomes `canon_p1_search(s, g, root, max_nodes)` with the leaf doing `act_into` and `stream_write` by kind. Keep the S1 subset path byte-identical: the S1 C tests and the S1 tier of `test_e2e.py` must pass unchanged. The leaf image for a graph is built into a reusable `canon_graph` in the workspace (arcs relabelled and re-sorted); the leaf bytes buffer is reused.

### 3.6 CLI

```
canon-cli p1-graph --n N --gens "..." [--colours "hex;hex;..."] [--arcs "s,t,labelhex,m;..."] [--max-nodes K] [--id CASE]
```

Empty `--colours` means all empty; a missing `--arcs` means no arcs; label hex may be empty. Same record format and exit codes as `p1-subset`. Reject ids beginning with `#`.
